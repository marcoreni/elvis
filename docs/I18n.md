# Internationalisation (i18n)

Ce document explique comment fonctionne la traduction dans Elvis et comment ajouter une nouvelle
langue. Pour le contexte du chantier (pourquoi, découpage en branches, avancement), voir
[I18n-Roadmap.md](I18n-Roadmap.md).

> Ce document est complété au fil des branches `feature/i18n-0N-*`.

## Langues supportées

Les codes de langue pour lesquels le code base fournit (ou fournira) des fichiers de traduction
sont définis dans `Elvis::SUPPORTED_LOCALES` (`lib/elvis/supported_locales.rb`). C'est la seule
liste à modifier pour qu'une langue devienne éligible dans tout le reste du système (résolution de
locale, validation `config.i18n.available_locales`, sélecteur de langue).

Une installation peut en outre restreindre les langues qu'elle propose réellement à ses
utilisateurs via l'écran d'administration "Paramètres > Langues"
(`Parameters::LocalizationParametersController`, réglage `app.localization.available_languages`)
— un sous-ensemble de `Elvis::SUPPORTED_LOCALES`. `ApplicationController#available_locales`
(`helper_method`, utilisable aussi bien dans les contrôleurs que les vues) calcule ce
sous-ensemble effectif et c'est lui qui doit être utilisé partout où la liste des langues
proposées à un utilisateur est affichée — pas `Elvis::SUPPORTED_LOCALES` directement, qui
représente seulement ce que le code sait traduire, pas ce qu'une installation donnée a choisi
d'activer.

## Résolution de la locale (backend)

Pour chaque requête, `ApplicationController#switch_locale` (un `around_action` posé en premier,
donc englobant tout le reste, y compris les contrôleurs Devise qui héritent eux aussi
d'`ApplicationController` via `Devise::*Controller` < `DeviseController` < `ApplicationController`)
résout la locale effective dans cet ordre :

1. `current_user.locale` — préférence enregistrée de l'utilisateur connecté
2. Le cookie `locale` — invité, ou navigateur déconnecté ayant déjà choisi une langue
3. `Parameter.get_value("app.localization.default_language")` — langue par défaut de l'installation
4. `I18n.default_locale` (`:fr`) — filet de sécurité final

La locale résolue est toujours validée contre `available_locales` (voir ci-dessus) avant d'être
appliquée (`config.i18n.available_locales` est désormais réellement appliqué —
`enforce_available_locales` est actif — donc une locale non supportée lève une erreur plutôt que
d'échouer silencieusement).

Changer de langue se fait via `PATCH /locale` (route nommée `locale`, voir
`app/controllers/locale_controller.rb`), qui pose le cookie et met à jour
`current_user.locale` si l'utilisateur est connecté. Le sélecteur de langue
(`app/views/partials/_language_switcher.html.erb`) est inclus dans les trois layouts
(`application.html.erb`, `devise.html.erb`, `simple.html.erb`) pour fonctionner aussi bien sur les
pages Devise (connexion, inscription...) que dans l'application connectée.

## Convention de nommage des clés (backend)

Fichiers YAML sous `config/locales/`, un fichier par langue (`fr.yml` est la langue de base,
`en.yml` la première langue traduite). Organisation des clés :

- `views.<controller>.<action>.<clé>` — texte spécifique à une vue
- `activerecord.models.*` / `activerecord.attributes.*` — noms de modèles/attributs, repris
  automatiquement par les helpers de formulaire Rails (`form_for`, `label`, etc.)
- `common.actions.*` / `common.confirm.*` — texte partagé entre plusieurs vues (boutons
  "Enregistrer"/"Annuler", dialogues de confirmation de suppression) pour éviter la duplication
- `translate_enum` (voir `app/models/activity_ref.rb`) garde sa propre convention
  (`activerecord.attributes.<model>.<enum>_list.<value>`), ne pas la dupliquer ailleurs

## Pluriel

Natif à Rails/`rails-i18n`, pas de gem supplémentaire : `I18n.t(key, count: n)` avec des clés
YAML `one`/`other` :

```yaml
fr:
  users:
    count:
      one: "%{count} élève"
      other: "%{count} élèves"
```

## Interpolation

Syntaxe Rails native `%{name}` :

```yaml
fr:
  users:
    greeting: "Bonjour %{first_name}"
```

## Texte riche / HTML

Utiliser la convention Rails des clés suffixées `_html` (auto-marquées `html_safe` par les
helpers de vue) — uniquement pour du markup rédigé par les traducteurs, jamais pour interpoler du
contenu utilisateur :

```yaml
fr:
  cgu:
    intro_html: "Voir nos <a href=\"/cgu\">conditions d'utilisation</a>."
```

## Résolution de la locale (frontend)

`frontend/i18n/index.js` initialise i18next (`react-i18next` + `i18next-browser-languagedetector`)
et est importé en tout premier dans `frontend/packs/app.js`, avant l'enregistrement des composants
React (`ReactRailsUJS.useContext`). La langue initiale est lue directement depuis
`document.documentElement.lang` (le `<html lang="...">` posé côté serveur par
`ApplicationController#switch_locale`, voir plus haut) — pas de nouvel objet "bootstrap" global
côté JS, la locale ERB et la locale React sont donc déjà synchronisées au premier rendu. Le
détecteur retombe sur `localStorage` puis `navigator` uniquement si `<html lang>` est absent.

`moment` est resynchronisé automatiquement sur l'événement `i18next` `languageChanged`
(`moment.locale(lng)`). Les anciens `require("moment/locale/fr")` individuels dans les composants
ont été retirés (effet de bord problématique : cela forçait la locale *globale* de moment à "fr" à
chaque montage du composant, indépendamment de la langue choisie, défaisant cette synchronisation)
— seul `frontend/i18n/index.js` importe désormais un fichier de locale moment. Ne jamais réintroduire
un `require`/`import "moment/locale/..."` dans un composant individuel ; passer par ce fichier
central.

## Convention de nommage des clés (frontend)

Fichiers JSON sous `frontend/locales/<locale>/<namespace>.json`, un namespace par dossier de
premier niveau sous `frontend/components/<feature>/` (ex. `users`, `activities`, `planning`), plus
un namespace `common` pour le texte partagé (boutons SweetAlert2, en-têtes de tableau). Utiliser
`useTranslation()` (composants fonction) ou le HOC `withTranslation()` (composants classe — la
base de code en a encore beaucoup, `useTranslation` seul ne suffit pas).

Depuis un composant enveloppé dans `withTranslation("<feature>")`, on cible une clé d'un autre
namespace avec le préfixe `ns:` — ex. `t("common:reactTable.previousText")`.

**Clés partagées `common` déjà en place** — les réutiliser, ne pas les redéclarer par namespace :

- `common.actions.{save,cancel}` (JSON frontend) — boutons génériques.
- `common.reactTable.{previousText,nextText,loadingText,noDataText,pageText,ofText,rowsText}` —
  les sept props de traduction de `react-table`. Tout composant montant une `<ReactTable>` /
  `<ReactTableFullScreen>` doit passer ces clés (`previousText={t("common:reactTable.previousText")}`
  …) plutôt que des chaînes en dur ou une copie par namespace. (`UserList` était le premier
  consommateur ; les clés vivaient d'abord dans `users.json` sous `list.table.*` puis ont été
  promues dans `common` — voir la branche `feature/i18n-common-react-table-keys`.)

## Pluriel (frontend)

Natif à i18next, suffixes de clé `_one`/`_other` :

```json
{ "count_one": "{{count}} élève", "count_other": "{{count}} élèves" }
```

```jsx
t("count", {count: n})
```

## Interpolation (frontend)

Syntaxe i18next native `{{name}}` (volontairement différente du `%{name}` Rails — chaque stack
interpole ses propres chaînes déjà finalisées, un composant React ne doit jamais recevoir une clé
brute + placeholders à ré-interpoler côté client) :

```json
{ "greeting": "Bonjour {{firstName}}" }
```

## Texte riche (frontend)

Utiliser `<Trans i18nKey="...">` de `react-i18next` pour du texte contenant du markup ou des
éléments React (liens, gras), jamais `dangerouslySetInnerHTML`. Si du HTML brut est vraiment
inévitable, passer par `isomorphic-dompurify` (déjà une dépendance du projet) avant de l'injecter.

## Hors périmètre

Les emails `NotificationTemplate` (Liquid + WYSIWYG, stockés en base, rédigés par l'admin de
chaque instance — voir `docs/EventListeners.md`) et les autres textes pilotés par `Parameter` ne
font pas partie de ce chantier. C'est de la rédaction de contenu par instance, pas de la
traduction de l'interface.

## Exception documentée

`app/views/payments/bill.html.erb` fige volontairement `I18n.with_locale("fr")` pour certaines
dates : un document fiscal/légal français doit rester en français quelle que soit la langue de
l'interface de l'utilisateur qui le consulte. Ne pas "corriger" ce point sans revalider le besoin
métier/légal auprès de l'équipe produit.

## Ajouter une nouvelle langue

1. Ajouter le code de langue à `Elvis::SUPPORTED_LOCALES` (`lib/elvis/supported_locales.rb`).
2. Créer `config/locales/<code>.yml` (copier la structure de `fr.yml`).
3. Vérifier qu'une locale `devise-i18n` existe pour ce code (sinon, écrire
   `config/locales/devise.<code>.yml` à la main à partir de `devise.en.yml`).
4. Créer `frontend/locales/<code>/*.json` pour chaque namespace (copier la structure du
   namespace `fr` correspondant) et les ajouter à l'objet `resources` dans `frontend/i18n/index.js`
   — `SUPPORTED_LOCALES` en est dérivé automatiquement (`Object.keys(resources)`), pas besoin de le
   modifier à la main. Importer aussi le fichier de locale moment correspondant
   (`import "moment/locale/<code>"`) dans ce même fichier : sans ça, `moment.locale(...)` ne prendra
   pas effet pour cette langue.
5. Ajouter le code à `locales` dans `i18next-parser.config.js` — sans ça, `yarn i18n:extract` (étape
   suivante) ignore silencieusement la nouvelle langue et ne remonte aucune clé manquante pour elle.
6. Lancer `bundle exec i18n-tasks health` (backend) et `yarn i18n:extract` (frontend, config
   `i18next-parser.config.js`) pour lister les clés manquantes.
7. Traduire les clés manquantes.
8. Activer la langue pour l'installation via l'écran d'administration "Paramètres > Langues"
   (`/parameters/localization_parameters`).

## Outillage

- `bundle exec i18n-tasks health` / `missing` / `unused` / `normalize` (config : `.i18n-tasks.yml`)
  — santé des clés côté backend.
- `yarn i18n:extract` (config : `i18next-parser.config.js`) — scanne `frontend/{components,tools,packs}/**`
  à la recherche des appels `t(...)`/`<Trans>` et synchronise
  `frontend/locales/<locale>/<namespace>.json` en conséquence.
