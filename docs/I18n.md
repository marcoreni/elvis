# Internationalisation (i18n)

Ce document explique comment fonctionne la traduction dans Elvis et comment ajouter une nouvelle
langue. Pour le contexte du chantier (pourquoi, découpage en branches, avancement), voir
[I18n-Roadmap.md](I18n-Roadmap.md).

> Ce document est complété au fil des branches `feature/i18n-0N-*`. La partie backend ci-dessous
> est posée par `feature/i18n-01-foundation-backend`. La partie frontend (i18next/react-i18next)
> sera ajoutée par `feature/i18n-02-foundation-frontend`.

## Langues supportées

Les codes de langue pour lesquels le code base fournit (ou fournira) des fichiers de traduction
sont définis dans `Elvis::SUPPORTED_LOCALES` (`lib/elvis/supported_locales.rb`). C'est la seule
liste à modifier pour qu'une langue devienne éligible dans tout le reste du système (résolution de
locale, validation `config.i18n.available_locales`, sélecteur de langue).

Une installation peut en outre restreindre les langues qu'elle propose réellement à ses
utilisateurs via le réglage admin "langues disponibles" (`app.localization.available_languages`,
voir `feature/i18n-03-localization-settings`) — un sous-ensemble de `Elvis::SUPPORTED_LOCALES`.

## Résolution de la locale (backend)

Pour chaque requête, `ApplicationController#switch_locale` (un `around_action` posé en premier,
donc englobant tout le reste, y compris les contrôleurs Devise qui héritent eux aussi
d'`ApplicationController` via `Devise::*Controller` < `DeviseController` < `ApplicationController`)
résout la locale effective dans cet ordre :

1. `current_user.locale` — préférence enregistrée de l'utilisateur connecté
2. Le cookie `locale` — invité, ou navigateur déconnecté ayant déjà choisi une langue
3. `Parameter.get_value("app.localization.default_language")` — langue par défaut de l'installation
4. `I18n.default_locale` (`:fr`) — filet de sécurité final

La locale résolue est toujours validée contre `Elvis::SUPPORTED_LOCALES` avant d'être appliquée
(`config.i18n.available_locales` est désormais réellement appliqué —
`enforce_available_locales` est actif — donc une locale non supportée lève une erreur plutôt que
d'échouer silencieusement).

Changer de langue se fait via `PATCH /locale` (route nommée `locale`, voir
`app/controllers/locale_controller.rb`), qui pose le cookie et met à jour
`current_user.locale` si l'utilisateur est connecté. Le sélecteur de langue
(`app/views/partials/_language_switcher.html.erb`) est inclus dans les trois layouts
(`application.html.erb`, `devise.html.erb`, `simple.html.erb`) pour fonctionner aussi bien sur les
pages Devise (connexion, inscription...) que dans l'application connectée.

## Convention de nommage des clés (backend)

Fichiers YAML sous `config/locales/`, un fichier par langue (`fr.yml` est la langue de base,
`en.yml` la première langue traduite). Organisation des clés :

- `views.<controller>.<action>.<clé>` — texte spécifique à une vue
- `activerecord.models.*` / `activerecord.attributes.*` — noms de modèles/attributs, repris
  automatiquement par les helpers de formulaire Rails (`form_for`, `label`, etc.)
- `common.actions.*` / `common.confirm.*` — texte partagé entre plusieurs vues (boutons
  "Enregistrer"/"Annuler", dialogues de confirmation de suppression) pour éviter la duplication
- `translate_enum` (voir `app/models/activity_ref.rb`) garde sa propre convention
  (`activerecord.attributes.<model>.<enum>_list.<value>`), ne pas la dupliquer ailleurs

## Pluriel

Natif à Rails/`rails-i18n`, pas de gem supplémentaire : `I18n.t(key, count: n)` avec des clés
YAML `one`/`other` :

```yaml
fr:
  users:
    count:
      one: "%{count} élève"
      other: "%{count} élèves"
```

## Interpolation

Syntaxe Rails native `%{name}` :

```yaml
fr:
  users:
    greeting: "Bonjour %{first_name}"
```

## Texte riche / HTML

Utiliser la convention Rails des clés suffixées `_html` (auto-marquées `html_safe` par les
helpers de vue) — uniquement pour du markup rédigé par les traducteurs, jamais pour interpoler du
contenu utilisateur :

```yaml
fr:
  cgu:
    intro_html: "Voir nos <a href=\"/cgu\">conditions d'utilisation</a>."
```

## Hors périmètre

Les emails `NotificationTemplate` (Liquid + WYSIWYG, stockés en base, rédigés par l'admin de
chaque instance — voir `docs/EventListeners.md`) et les autres textes pilotés par `Parameter` ne
font pas partie de ce chantier. C'est de la rédaction de contenu par instance, pas de la
traduction de l'interface.

## Exception documentée

`app/views/payments/bill.html.erb` fige volontairement `I18n.with_locale("fr")` pour certaines
dates : un document fiscal/légal français doit rester en français quelle que soit la langue de
l'interface de l'utilisateur qui le consulte. Ne pas "corriger" ce point sans revalider le besoin
métier/légal auprès de l'équipe produit.

## Ajouter une nouvelle langue

1. Ajouter le code de langue à `Elvis::SUPPORTED_LOCALES` (`lib/elvis/supported_locales.rb`).
2. Créer `config/locales/<code>.yml` (copier la structure de `fr.yml`).
3. Vérifier qu'une locale `devise-i18n` existe pour ce code (sinon, écrire
   `config/locales/devise.<code>.yml` à la main à partir de `devise.en.yml`).
4. *(à partir de `feature/i18n-02-foundation-frontend`)* Créer
   `frontend/locales/<code>/*.json` pour chaque namespace.
5. Lancer `bundle exec i18n-tasks health` pour lister les clés manquantes, et l'équivalent
   frontend une fois `feature/i18n-02` posé.
6. Traduire les clés manquantes.
7. Activer la langue pour l'installation via l'écran de réglages "Langues disponibles"
   (`feature/i18n-03-localization-settings`).

## Outillage

- `bundle exec i18n-tasks health` / `missing` / `unused` / `normalize` (config :
  `.i18n-tasks.yml`) — santé des clés côté backend.
- Équivalent frontend (`i18next-parser`) à documenter ici une fois posé par
  `feature/i18n-02-foundation-frontend`.
